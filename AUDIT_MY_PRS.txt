1. ОБЩАЯ ОЦЕНКА
--------------------------------------------------------------------------------
Твои PR составляют основной фундамент HyperHLE-Reborn: Android/iOS UX (локсрин и
домашний экран в стиле iOS 4, Settings, менеджер файлов через SAF), исправления
рендера на Adreno/Mali, транслятор GLES1-on-GLES2, MSAA resolve, CoreText,
StoreKit IAP, реальный HTTP/HTTPS, сокеты в read()/write(), Mach vm_read_overwrite,
обход падений на диких PC и кэширование JNI на основном потоке Android.

Тем не менее при строгой проверке исходного кода в ряде твоих влитых PR нашлись
реальные баги (включая 1 критический баг затирания регистра r0 в ABI, 1 гарантированный
краш при вызове метода в NSProgress и 1 важную проблему безопасности с публичным
Android release.keystore). Ниже приведён честный и подробный разбор.

2. БЕЗОПАСНОСТЬ РЕЛИЗОВ И РЕПОЗИТОРИЯ
================================================================================

[ВАЖНО] Публичный ключ подписи Android APK лежит прямо в Git с паролем в открытом виде
Файлы:
  - android/keystore/release.keystore
  - android/app/build.gradle:53-77

Суть проблемы:
  В репозитории закоммичен `android/keystore/release.keystore`, а в `build.gradle`
  прописаны дефолтные пароль и алиас:
    def hyperHLEKeystorePass = System.getenv('HYPERHLE_KEYSTORE_PASSWORD') ?: 'hyperhle'
    def hyperHLEKeyAlias = System.getenv('HYPERHLE_KEY_ALIAS') ?: 'hyperhle'

  Если в GitHub Secrets репозитория не задан `HYPERHLE_KEYSTORE_B64` (или при
  локальной/форк-сборке), релизный `HyperHLE-Reborn.apk` подписывается этим
  публичным ключом. Это значит, что любой посторонний человек может собрать
  вредоносный APK с `applicationId = org.hyperhle.reborn` и подписать его ТЕМ ЖЕ
  ключом — Android позволит установить поддельный «апдейт» поверх оригинала с
  полным доступом к данным приложения.

Что сделать:
  Убедиться, что в GitHub Secrets задан приватный `HYPERHLE_KEYSTORE_B64`, а
  публичный `android/keystore/release.keystore` перевести только в debug/dev-режим
  или удалить из `signingConfigs.release`.

3. КРИТИЧЕСКИЕ И СЕРЬЁЗНЫЕ БАГИ В ТВОИХ ВЛИТЫХ PR
================================================================================

[БАГ #1 — КРИТИЧЕСКИЙ ABI] Затирание указателя исключения r0 нулём при пробросе
                           в гостевой SjLj-рантайм
PR: #273 ("Fix endless Il2CppExceptionWrapper throw loop")
Файлы:
  - src/libc/cxxabi.rs:301-326, 881-885, 938-945
  - src/abi.rs:138-145

Техническая суть:
  `forward_to_guest_cxxabi(env, "__Unwind_SjLj_RaiseException", &[exc.to_bits()])`
  записывает `exc` в `regs[0]`, перенаправляет `PC` на гостевую функцию и ставит
  флаг `env.note_guest_control_flow_redirect()`.

  НО обёртки `_Unwind_SjLj_RaiseException` и `_Unwind_SjLj_Resume_or_Rethrow`
  имеют возвращаемый тип `-> i32` и после `forward_to_guest_cxxabi(...)` делают
  `return 0;`!
  Сразу после возврата из Rust-функции `CallFromGuest::call_from_guest`
  (src/abi.rs:143 — ещё ДО проверки `guest_control_flow_redirected` в
  src/environment.rs:3563!) выполняет:
    `retval.to_regs(env.cpu.regs_mut());`
  и ЗАТИРАЕТ `regs[0]` значением `0` (`NULL`)!

  В итоге гостевой `__Unwind_SjLj_RaiseException(exc)` получает `r0 = NULL` вместо
  указателя на объект исключения. (Для `__cxa_throw` и `_Unwind_SjLj_Resume` с
  типом `-> ()` баг не проявляется, а для функций с `-> i32` ломает r0).

Как исправить:
  В `src/abi.rs:140` (и `169`) не записывать `retval` в регистры/память, если
  установлен `env.is_guest_control_flow_redirected()`.

[БАГ #2 — ВЫСОКИЙ] Гарантированное падение в -[NSProgress setUserInfoObject:forKey:]
                   + утечка retain
PR: #276 ("Fix wild-PC trap hangs and fill in Foundation gaps for Unity SDKs")
Файл: src/frameworks/foundation/ns_progress.rs:64-71, 200-218

Техническая суть (сразу 4 ошибки в одном классе):
  1) В `setUserInfoObject:forKey:` при `user_info == nil` создаётся
     `NSMutableDictionary`, затем вызывается `let dict: id = msg![env; dict copy];`
     — метод `-copy` возвращает НЕИЗМЕНЯЕМЫЙ `NSDictionary`! На следующей же строке
     вызывается `msg![env; dict setObject:object forKey:key]`, что гарантированно
     падает на отсутствии селектора `setObject:forKey:` у `NSDictionary`.
     То же самое произойдёт, если в `initWithParent:userInfo:` передали обычный
     `NSDictionary` (он сохраняется без `mutableCopy`).
  2) В Apple Foundation вызов `[progress setUserInfoObject:nil forKey:key]` удаляет
     ключ (`removeObjectForKey:`), а сейчас передаёт `nil` в `setObject:forKey:`.
  3) Перед `setObject:object forKey:key` вызывается лишний `retain(env, object)` —
     словари сами делают `retain`, поэтому каждый вызов даёт утечку +1 refcount.
  4) `cancellable` по умолчанию `false` (в iOS у `NSProgress` по умолчанию `YES`),
     а `-userInfo` возвращает `nil` вместо пустого `NSDictionary` (`@{}`).

[БАГ #3 — ВЫСОКИЙ] Copy-on-Write для файлов бандла IPA теряет изменения при
                   чтении (O_RDONLY) на следующем запуске игры + обход путей
PR: #37 ("fix: Copy-on-Write for IPA bundle files + UITouch lifecycle fix")
Файл: src/fs.rs:1131-1155, 1699-1742

Техническая суть:
  1) При первом запуске, когда игра открывает файл внутри `.app` на запись,
     `CowIpa` извлекает его в `sandbox/<bundle_id>/bundle_cow/...` и в памяти
     переключает узел VFS на `FileLocation::Path(host_path)`.
     НО при СЛЕДУЮЩЕМ запуске игры `Fs::new` заново строит дерево бандла из `.ipa`
     (`FileLocation::IpaFileRef`, `writeable = false`), НЕ накладывая поверх него
     уже существующие файлы из `bundle_cow/`!
     Поэтому когда при втором запуске игра открывает этот же файл ТОЛЬКО НА ЧТЕНИЕ
     (`O_RDONLY`, `write == false`), условие `if !writeable && (append || write)`
     не срабатывает, и игра читает старый немодифицированный файл из `.ipa`!
  2) Путь в `bundle_cow` строится из сырого `path.as_str()`
     (`rel.split('/').fold(cow_base, |acc, c| acc.join(c))`), а не из
     канонического VFS-пути: относительный `open("config.ini", O_RDWR)` и
     абсолютный путь попадают в разные места внутри `bundle_cow`, а сегменты `..`
     не нормализуются перед `join` (возможен выход за пределы `bundle_cow`).

[БАГ #4 — СРЕДНИЙ/ВЫСОКИЙ] Выход за границу 4 КБ буфера `null_page` при C/GL вызовах
                           и паника `copy_from_slice` на границе страницы
PR: ранние PR по памяти (#11 / #23 и связанные правки `null_page`)
Файл: src/mem.rs:754-895

Техническая суть:
  В `bytes_at` и `bytes_at_mut` при попадании адреса в `null_segment` или за
  пределы 4 ГБ возвращается срез из `self.null_page` (размером 4096 байт) длины
  `actual_count = count_usize.min(PAGE_SIZE - offset)`:
  1) Если `count > PAGE_SIZE - offset` (например `ptr = 0xFF0, count = 64` или
     `ptr = 0x0, count = 8192`), функция возвращает срез МЕНЬШЕЙ длины, чем
     просил вызывающий код! Любой вызов `.copy_from_slice(&src[..count])` тут же
     роняет эмулятор с Rust panic (`source slice length != destination slice length`).
  2) Ещё опаснее в `ptr_at` / `ptr_at_mut` (src/mem.rs:864): они возвращают сырой
     указатель на 4-килобайтную `self.null_page` даже когда `size = 65536`!
     Передача такого указателя в OpenGL (`glTexImage2D`, `glBufferData`) или C-код
     приводит к чтению/записи за пределами 4 КБ в куче хоста (host SIGSEGV / UB).

4. СРЕДНИЕ И МЕЛКИЕ НЕДОЧЁТЫ В ТВОИХ PR
================================================================================

1) PR #207 ("Add real HTTP(S) URL loading support" — url_loading.rs):
   * Утечка NSError (src/frameworks/foundation/url_loading.rs:530-535):
     `make_foundation_error` уже делает `autorelease`, а `write_error_out_parameter`
     сверху вызывает ещё и `retain(env, error)`. По конвенции ObjC `NSError **` —
     это `__autoreleasing`, поэтому каждый ошибочный запрос оставляет неубитый NSError.
   * Двойная аллокация в гостевой куче (url_loading.rs:495-505):
     `make_foundation_response` выделяет до 256 МБ через `env.mem.alloc`, копирует
     тело, а затем `NSData dataWithBytes:length:` выделяет ВТОРЫЕ 256 МБ (пик 512 МБ).
     Лучше отдавать буфер через `dataWithBytesNoCopy:length:freeWhenDone:true`.
   * Синхронный `url_loading::send()` (url_loading.rs:384):
     блокирует весь поток хоста (до 60–300 сек) вместо `send_async` + `env.sleep()`,
     из-за чего синхронная загрузка во вторичном гостевом pthread замораживает окно
     и звук всего эмулятора.

2) PR #61 ("Add experimental GLES1 to GLES2 translator" — src/gles/gles1_on_gles2.rs):
   * В `BufferData` (строка 2166): `bytes.resize(size as usize, 0)` без проверки
     `size < 0` (`GLsizeiptr` знаковый!) — отрицательный размер вызовет panic по
     переполнению памяти вместо `GL_INVALID_VALUE`.
   * В `DeleteBuffers` (строка 2140): `buffers.add(i).read()` читает `u32` без
     учёта невыровненного гостевого указателя (нужен `read_unaligned()`).

3) PR #180 ("App picker: delete apps via long-press" — src/environment/app_picker.rs):
   * На строках 190-198 базы SQLite удаляются по префиксу `"{bundle_id}_"`. Если
     установлены две игры с общим префиксом (например `com.foo.game` и
     `com.foo.game_hd`), удаление первой сотрёт сохранения второй!
   * Если в папке лежат две версии `.ipa` одной игры с одинаковым `bundle_id`,
     удаление одной сносит общую песочницу `sandbox/<bundle_id>` второй.

4) PR #148 / #261 (JNI в `src/android_web_view.rs:116-124`):
   * `exception_pending` вызывает JNI `ExceptionOccurred` (слот 15), который
     создаёт локальную ссылку `jthrowable`, и не освобождает её через
     `DeleteLocalRef` (лучше использовать `ExceptionCheck`, слот 228, не создающий
     локальных ссылок).

5) PR #133 ("Fix detached EAGL view for Asphalt 8" — src/frameworks/opengles/eagl.rs:3436):
   * `attach_orphaned_eagl_view_to_root` внутри `presentRenderbuffer:` вызывает
     `[root_view_controller view]`. Если вьюха контроллера ещё не была загружена
     (`isViewLoaded == false`), это реентерабельно запустит `-loadView` /
     `-viewDidLoad` прямо посреди презентации кадра OpenGL.

6) PR #276 (`src/frameworks/foundation/ns_data.rs:344-354`):
   * Метод `-[NSData base64EncodedDataWithOptions:]` (добавлен в твоём #276) не
     учитывает флаги переноса строк `NSDataBase64Encoding64CharacterLineLength` и
     `76CharacterLineLength` в параметре `options`.

7) Мусорные файлы и именование PR в репозитории:
   * В корне и `tests/` закоммичены отладочные скриншоты и логи (~1.4 МБ):
     - `Picsart_26-10-20_10-43-04-335.jpg` (919 КБ)
     - `geometry-dash-gameplay-proof.png` (137 КБ)
     - `geometry-dash-level-proof.png` (136 КБ)
     - `mutant-fridge-title-screen.png` (118 КБ)
     - `3d-coaster-perform-selector.png`
     - `tests/1.txt` (60 КБ лог запуска Turbo Dismount на Android)
   * Серия крупных пакетных PR (#74, #76, #77, #78, #81, #88, #98, #101, #108, #123)
     влита с авто-заголовками `Arena/01a0... hyperhle fork`, что затрудняет поиск
     регрессий через историю PR.

   `guest_control_flow_redirected` (чинит r0 в PR #273).

   убрать лишний `retain(env, object)` и выставить `cancellable = true` (PR #276).
